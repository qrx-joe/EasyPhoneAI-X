## P1 问题

### P1-1 medium 风险档未完整接线 + 教程 `maxLevel` 声明了但未强制执行

**问题描述**

`tutorial.ts` 第 55 行明确声明契约：「风险等级 >= 教程 maxLevel 时，即使匹配上也不展示教程（必须走风险页）」。但该约束在决策链中**从未执行**：

- `safeTutorialsFor(level)`（`src/domain/guidance/tutorial.ts` 第 95 行）只做了两件事：
  1. `shouldStopGuidance(level)` 早退（只对 high/critical 生效）；
  2. `TUTORIALS.filter((t) => !shouldStopGuidance(t.maxLevel))`（只过滤掉 maxLevel 为 high/critical 的教程）。
  
  它**没有拿入参 `level` 去和每个教程的 `maxLevel` 比较**。

- `decideNext`（`src/application/decide-next.ts` 第 168–188 行）：先 `findTutorial` 拿到教程，随后只检查 `safeTutorialsFor(merged.level).length === 0`。由于库里 3 个教程的 `maxLevel` 均为 `low`/`medium`，该条件对 low/medium **恒为非空**，等于恒等通过；之后直接取 `tutorial.steps[0]`，**从不检查 `tutorial.maxLevel` 与 `merged.level` 的关系**。

- `guideNextStep`（`src/application/guide-next-step.ts` 第 41–64 行）同样只查 `shouldStopGuidance(risk)`，不查 `tutorial.maxLevel`。

**可复现的错误**

输入「微信没声音 对方问我手机号」：
- `手机号` 命中 medium → `merged = medium`
- `findTutorial` 命中 `wechat-no-sound`（其 `maxLevel: 'low'`）
- 系统返回 `risk: 'medium'` + 步骤「打开微信」

结果：一个隐私风险（被索取手机号）被一个**不相关的低风险教程**吞掉，且**没有任何 medium 应有的「二次确认」**。

**连带影响（medium 档整体半成品）**

README §2.2 / `types.ts` 定义 medium 为「教程可继续，但需要额外的二次确认步骤」。实际：
- medium 命中退款教程 → 靠退款教程步骤内自带警告勉强兜住；
- medium 命中低风险教程 → 给错教程（上述复现）；
- medium 不命中任何教程（如单独「对方问我手机号」）→ `TASK_STATE_NOT_FOUND`，而 medium 的谨慎建议（`SUGGESTIONS_BY_LEVEL.medium`）**从未被展示**——`buildHandoff` 虽支持 medium，但决策链里 medium 从不走 stop、也不产出求助卡。

**为什么不是 P0**

high/critical 仍在 `decide-next.ts` 第 135 行先于 `findTutorial` 走 stop，不会漏放高危。medium 档的缺陷是「谨慎度不足 / 给错教程」，不是「把高危放行」。

**测试覆盖缺口**

`src/application/decide-next.test.ts` 没有「medium 命中 low 教程」场景；`src/domain/guidance/tutorial.test.ts` 只断言 `safeTutorialsFor('high'|'critical').length === 0`，未断言 `level` 与 `t.maxLevel` 的比较逻辑。

**建议修复**

在 `decideNext` 与 `guideNextStep` 中，对找到的教程补一条硬校验：

```ts
if (RISK_RANK[merged.level] > RISK_RANK[tutorial.maxLevel]) {
  // 返回 clarify 或 unsupported，绝不给高于 maxLevel 的教程
}
```

并补测试：「medium 命中 low 教程 → 不返回 guide」。同时明确 medium 的「二次确认」产出（或显式标注 P0 暂缓并写入证据清单）。

### P1-2 求助卡对象携带原始输入，与 §10.1「不含验证码/卡号」名实不符

**问题描述**

`HandoffCard` 包含 `question`（`QuestionRecord`），其中 `question.text` 是**用户原始输入**。`createQuestion`（`src/domain/question/question.ts`）只做 `trim`，**不做任何脱敏**。

若老人把「验证码是 123456」「卡号 6222…」这类内容敲进输入框，它会原样进入 `decision.handoff.question.text`，并随 `/api/v2/decision` 的响应 JSON 返回。

**与声明的冲突**

`src/application/build-handoff.ts` 注释与 README §10.1 明确写着：「求助卡不得包含 OTP、验证码、支付密码、完整银行卡号、身份凭据」。

**缓解项（因此不是 P0，而是 P1）**

- 真正分享给家人的文本 `serializeHandoffCard`（`src/domain/handoff/card-serialization.ts`）只用 `summary` + `suggestions`，**不含** `question.text`。
- 两个 UI（`assist-client.tsx`、`risk-alert-client.tsx`）都不渲染 `question.text`。

所以实际泄露面 = API 响应 JSON + 服务端对象，而非分享出去的内容。但声称与实现之间的落差依然存在。

**测试覆盖缺口**

`src/domain/handoff/handoff.test.ts` 第 110 行的「安全约束」测试**只检查 `summary` + `suggestions`**，没有检查 `question.text` 是否含 OTP/卡号——正好漏掉这个面。

**建议修复**

在 `createQuestion` 或 `buildHandoffCard` 处对 `question.text` 做脱敏（正则抹除 11 位手机号、连续 4+ 位数字、疑似卡号形态），并补一条「question.text 不含 OTP/卡号」的测试。

## P2 问题

### P2-1 两条并行路由流 + 死代码（「新目标破坏旧功能」的漂移证据）

**问题描述**

存在两套并行的「生产路由」，而 README 第 24 行声称「三条路径使用同一套生产路由」：

1. **真实主流程（新）**：`src/app/home-client.tsx` 第 51 行直接 `router.push('/assist?text=…')` → `/assist` → `submitDecision` → `/api/v2/decision` → `decideNext` → 内联渲染结果。
2. **遗留流（旧）**：`/confirm → /tutorial → /unknown` 页面，靠 `guardGuidanceRoute`（内部走 `buildRouteForInput`）防 deep-link 绕过。但 `home-client` 已**不再** `push('/confirm')`，此流只能靠手拼 URL 进入。

**死代码**

- `routeToInput`（`src/domain/routing/user-routing.ts` 第 90 行）在生产代码中**零调用**——grep 结果只有：定义处、`user-routing.test.ts`、以及 `voice-input-button.tsx` 第 14/28 行的**注释**。
- `buildRouteForInput` 只剩 `guardGuidanceRoute` 一个调用方。

**与声明冲突**

- `user-routing.ts` 注释自称「文本提交 / 语音输入 / demo 路由 / deep link 共用的**单一安全核心入口**」，但文本/语音实际走 `/assist`，绕过了它。
- `/tutorial` 页直接调 `findTutorial`（`src/app/tutorial/page.tsx` 第 30 行），绕过了 `decideNext` 的完整决策链（虽对纯文本等价，但把 P1-1 的 maxLevel 缺口也复制了一份）。

**影响**

安全上没有洞（遗留页有 guard 保护），但这是「用新流程替代旧流程时，旧流程既没退役也没重接」的典型漂移，且存在功能重复与维护双轨。

**建议修复**

二选一：
- **A**：让 `home-client` 重新走 `buildRouteForInput`（单一入口，统一两套流）；
- **B**：删除 `/confirm`、`/tutorial`、`/unknown` 遗留流与 `routeToInput` 死代码，只保留 `/assist` 决策 API 流，并同步修正 README 措辞。

## P3 问题（一致性小问题，可排期清理）

### P3-1 `findTutorial` 未做全角→半角归一

`findTutorial`（`src/domain/guidance/tutorial.ts` 第 72 行）只做 `toLowerCase().trim()`，没有 `classifyRiskByRules` 里的 `fullToHalf`（`src/domain/risk/classify-risk.ts` 第 25 行）。全角输入（如 `ＷＥＣＨＡＴ`）会匹配失败。

**建议**：抽出公共 `normalize` 工具，两处共用。

### P3-2 文档与数据不符：「充值/充话费」声称降级到 medium，实际完全缺失

`src/domain/risk/risk-keywords.ts` 第 11 行注释写「「充值/充话费」=critical 降到 medium」，但关键词数据里**根本没有**这两条（第 55 行才承认「不在本桶」）。文档与数据不一致。

**建议**：修正注释，明确「已移除而非降级」，或补回 medium 级条目。

### P3-3 同一错误码两套语义（HTTP 200 vs 400）

`CONSENT_REQUIRED`、`INVALID_INPUT` 在 `decideNext`（`src/application/decide-next.ts` 第 95、103 行）作为 `unsupported` 决策返回 **HTTP 200**；而 `error-codes.ts` + `route.ts`（第 104–108 行）把它们定义为 **400 错误码**。

**影响**：仍安全（截图未被处理），但同一错误码出现两套语义，客户端与审计逻辑易混淆。

**建议**：统一为「决策级错误走 200 + reasonCode」或「参数错误走 400 错误响应」，二选一并写进契约。

### P3-4 定义未使用的代码

- `ERROR_CODES.VISION_TIMEOUT`、`RATE_LIMITED` 从未被 `decideNext` 产出（`src/contracts/error-codes.ts`）。
- `RiskAssessment.source` 与 `mergeRiskByMax` 返回的 `source: 'merged'` 无人消费（`src/contracts/risk-policy.ts`）。
- `guideNextStep` 独立成函数，但 `decideNext` 内联了同样逻辑，未复用（`src/application/guide-next-step.ts` vs `decide-next.ts` 第 168–194 行）。

**建议**：删除或用上，避免「看似有保障、实际未接线」的误导。
